# Seedance 2.5 提示词工程协议

本参考把官方公开资料中的 Seedance 2.5 能力，转译为 `Alpha-Filmos-video` 的保守编译策略。它负责提示词和参考职责的组织，不承诺平台一定按字面生成，也不虚构未公开的 API 字段。

## 模型工作方式

Seedance 2.5 应被当作全片级导演简报来写，而不是一条孤立的招式句。一次项目最多写 30 秒；更长内容使用多轮延长，并在每轮明确继承的角色、空间、光线、伤势、武器和声音状态。官方资料确认可组合图片、视频和音频参考，但“能够上传”不等于所有参考会同时进入画面：每个文件必须先分配唯一职责。

- ByteDance Seed：<https://seed.bytedance.com/en/blog/one-take-creation-flexible-referencing-introducing-seedance-2-5>

## 八段 Prompt 结构

按下列顺序组织项目级 Prompt；可以使用自然语言，但不要省掉时间轴和职责边界：

1. `format`：时长、画幅、输出形态和是否连续长镜头。
2. `subject`：人物/物体身份、数量、关系和不变量。
3. `action`：目标、攻防因果、接触、结果和状态传递。
4. `environment`：空间拓扑、材质、光线来源和可被动作改变的环境。
5. `camera`：一个段落一个主运镜，写触发、焦点、路径和落点。
6. `look`：风格、色彩、质感、运动清晰度和必要的局部正向锁。
7. `timing`：从 00 秒开始连续覆盖完整时长的累计区间。
8. `audio_and_constraints`：对白、音效、环境、音乐、资产连续性和局部风险约束。

## reference_role_manifest：参考职责协议

在 Prompt 中显式标注 `@Image 1`、`@Video 1`、`@Audio 1` 等输入的职责。推荐职责包括：

- `character_identity`：只锁脸、发型、服装、体态或角色身份，不继承参考图背景和姿势。
- `scene_layout`：只锁空间结构、地标、材质和光线方向，不继承其中人物身份。
- `prop_weapon`：只锁武器/道具形状、握持关系和材质，不继承拍摄角度之外的动作。
- `style`：只锁媒介、色彩、质感和视觉气质，不改变人物或空间事实。
- `motion_camera`：只提供动作节奏、运动路径或摄影机行为，不覆盖身份、服装和场景。
- `previs_blocking` / `clay_render`：只提供站位、姿态、路径、机位和 Blocking；明确排除代理外观、坐标、箭头、标记和 UI。
- `audio_dialogue`：只提供对白、声线、环境或音效职责，不改变画面动作因果。

同一实体的多张参考图必须以同一个 `entity` 分组，并在 `same_entity` 归一化组中说明各图互补的范围，例如“同一角色的正面身份、侧面服装和背面武器挂点”。不能让两张同一角色图分别隐式定义不同脸型、服装或年龄。

## 时间轴与战斗负载

- 30 秒项目按功能段编排，通常 4–6 段；不要用更多动作填满时长。
- 时间区间必须连续，从 `00–...s` 覆盖至项目结束，不留未定义空档。动作后的余势、呼吸、环境反应或镜头收束应写在前一段的结束状态或显式延续段中。
- 每段只保留一个主要动作、一个主运镜、一个明确结果和一个可继承结束状态；多人协同用因果接力，不同时启动多套独立技能。
- 高速打斗仍然先写可读的接触、受力和优势变化，再写速度、快切或局部子弹时间。高速固定块是项目级意图，不是每段都要同时执行的摄影清单。
- 跨段必须重复锁定关键身份、武器、伤势、屏幕方向、光线方向和空间地标；必要时使用 Clay Render/PREVIS 先固定 Blocking。

## 音频分层

对白、角色声线、接触音效、环境声、音乐和静默重音分开写。对白只使用用户提供或明确确认的原句；没有对白时不要补台词。音效确认接触和材质，不能替代可见命中；环境和音乐不能掩盖受力、脚步或武器方向。

## 时间戳局部编辑

编辑 Prompt 的 `timestamp_edit` 模式必须声明 `source`、`keep` 和 `changes`。每条变更限定一个时间段，并写“只改什么”；未列出的区间默认保留原视频的身份、动作、灯光、声音和剪辑。不要把全片重写伪装成局部编辑，也不要把未修改区间写成新的创作自由度。

## 证据边界

官方资料支持能力和工作流方向；本 Skill 的“单段单主动作、参考职责 manifest、累计时间轴、同实体归一化和局部保留”是稳定编译策略，不是平台官方硬限制。BytePlus API 能力以官方当前文档为准，未知字段保持未知；实际生成仍需在目标入口验证。
